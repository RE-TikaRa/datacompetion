# 赛题分析与实现约束

本赛题共 5 项顶层任务。原始依据为 `docs/competition/` 中的赛题 PDF，两份 Excel 仅提供标签和参考网站，四份 CSV 为提交格式模板，没有业务样本和标准答案。

## 1. 总体目标

用户提出需求方向，系统应自动触发一个采集批次。该批次经过采集、清洗、机会判别、主题聚合和价值排序，最终支持选题及立项策划。仅静态下载一批数据或展示现成图表，不能满足完整系统要求。

同一批次中必须有统一的记录身份和处理关系：

```text
批次需求与检索依据
  → 采集原始字段
  → 清洗记录与正文快照
  → 全部记录的机会判断
  → 机会记录组成主题簇
  → 主题簇维度分、总分与排名
  → 选定方向的策划案及来源引用
```

不同批次的数据、统计归一化、聚类和排名分别计算。底层模型可以复用，分析样本与输出不得在批次之间混合。

## 2. 附件理解

## 3. 假设敏感性预检

### 模糊表述及解释

| 表述 | 可能解释 | 对结果的影响 |
| --- | --- | --- |
| 近期热门 | 近期创建；近期有更新 | 只使用创建时间会遗漏长期维护项目；使用更新时间又不能将更新时间冒充发布时间 |
| 热门 | 全站热度最高；检索范围内相对热门 | 平台原始指标和检索排序不同，无法天然得到统一的热门定义 |
| 多源指向度 | 网站数量；来源类别数量 | GitHub 项目和 Issue 不能重复算作两个网站，两个资讯站也不代表两个来源类别 |
| 去重 | 相同内容与转载；同一主题的全部记录 | 后者会删除独立需求，导致热点统计失真 |
| 内容快照 | 完整正文；摘要或标题 | 仅有标题不支持与完整正文相同的机会判断可靠程度 |
| 置信度 | 校准概率；模型自评分或规则分 | 缺少验证时不能将自评分解释为已验证概率 |

### 快速验算与递进性检查

- 两条相似需求来自独立用户时，主题记录规模应为 2；同一文章复制到两站时，仍需记录共同来源，不能宣称存在两个独立需求。
- 100 条教程即使热度很高，命中排除规则后也不能进入机会主题聚合。
- 两站各 10 次浏览与一站 1,000 个星标的指标单位不同，不能通过简单相加比较价值。
- 只有一个主题簇时，按批次最小值和最大值归一化会出现零分母；评分规则需要在数学定义中覆盖这个情况。
- 一个批次没有机会记录时，result2 仍包含全部判断，result3 和 result4 保留表头，界面应解释没有可供评估的主题。

### 当前采用的解释

数据获取以近 90 个自然日的发布时间为范围，项目的更新时间单独保存。GitHub 取检索范围内按星标或讨论排序的记录，Hacker News 保留接口相关性与互动排序，资讯和订阅提供近期补充信号，各来源覆盖不能表述为完全一致。

网站覆盖和来源类别分别保留，任务三的网站覆盖按网站唯一计数。任务四的核心多源维度使用网站数，来源类别数可以作为补充信息，论文中需说明。完全重复与近重复分别处理，保留同主题的独立需求。

### 图像与对比表格

采集完成后可按来源绘制时间覆盖和记录数，检查样本偏向。判别阶段比较各来源、正文长度和记录类型上的准确性；聚类阶段展示语义簇及代表记录；排序阶段展示维度构成和权重变化下的排名稳定性。所有图表使用实际数据生成。

## 4. 任务一：多源采集与清洗

**输入：**需求方向、来源配置、检索条件、时间范围。**输出：**清洗记录、正文快照、去重映射及 result1。

记录至少包含批次号、连续编号、网站、来源链接、内容、发布时间、可用热度指标。主键为 `(batch_id, record_id)`；原始平台 ID 作为来源标识保留。

处理顺序为获取、字段规范化、隐私处理、HTML/渠道噪声清理、主题相关性筛选、重复识别和快照保存。缺失热度不填零，发布时间和更新时间分列。检索失败和结果截断进入清单，不能生成占位样本。

重复处理应先归并同一 URL 和完全重复正文，再评价近重复。近重复可使用词项指纹或语义相似度加来源证据，阈值用人工核验的重复对选择；相似主题不自动等于重复。

**校验：**批次内编号唯一且连续，所有正文可读取，链接与原始字段能对应，时间窗一致，去重前后数量可解释。采集召回率不能仅靠关键词命中数量证明，需要抽查遗漏和误收。

## 5. 任务二：机会判别与分类

**输入：**同批次全部清洗记录及标签体系。**输出：**每条记录的 0/1 判断、0～1 置信度，正例附一个功能和一个行业。

判定依据需要拆成可核验的证据：目标用户或业务场景、可观察痛点或寻解表达、AI 在解决路径中的核心作用、现成技术的可实现性，以及是否命中科普、纯教程、广告或营销噱头排除规则。

令 `q_i` 为模型原始自评值，令 `p_i=q_i`（机会）或 `p_i=1-q_i`（非机会），`t` 为机会候选阈值，`e_i` 表示是否命中排除条件。输出应满足 `e_i = 1` 时 `y_i = 0`，其余记录根据四项条件和 `q_i ≥ t` 判别。当前实现取 `t=0.5`，并将表 2 的机会置信度统一写成机会方向的 `p_i`。自评分与校准概率分别说明，不能将该列写成已验证概率。

评价样本需由人工按统一标准标注，覆盖正例、教程、宣传、正文不完整及难例。报告 Precision、Recall、F1、混淆矩阵和阈值选择；概率解释还需校准评价。功能与行业分别计算分类表现。

**校验：**result2 与 result1 的主键集合相同，非机会记录的功能和行业留空，正例标签来自明确版本的标签表。

## 6. 任务三：语义主题聚合

**输入：**任务二同批次正例。**输出：**主题簇、主题名称、代表分类、记录数、来源网站及成员编号。

语义表示应围绕用户、业务问题和解决目标，避免只按 AI、Agent 等技术词形成大簇。可比较文本向量加层次聚类或密度聚类，并使用人工同主题记录对和簇内一致性选择参数。模型与参数须记录，不能仅按功能或行业分组后宣称完成语义聚类。

令 `M_c` 为簇 c 的成员集合，`n_c = |M_c|`，`s_c` 为这些成员覆盖的不同网站数。主题命名必须概括成员共有的业务方向，并提供代表记录。密度聚类的噪声点不能静默消失，可保留为单记录主题或明示处理，成员覆盖关系要可解释。

评价包括适用条件下的轮廓系数、人工簇内一致性、主题可解释性和参数变化的稳定性。轮廓系数在主题数或样本数不满足条件时保留不可计算说明。

**校验：**成员均为同批次正例，编号存在，簇内数量与列表长度相同，来源集合从成员计算。单标签主题分配时，每条机会记录恰好归入一个主题。

## 7. 任务四：机会价值评分

**输入：**任务三主题及成员统计。**输出：**各维度 0～100 分、加权机会价值分和降序优先级。

必须包含多源指向度和记录规模。热度、需求明确程度、商业信号、时效性等可作为补充，但必须由已取得的真实字段或人工核验依据计算。文中没有足够依据的维度不参与评分。

令维度分为 `z_cj`，非负权重为 `w_j`，且 `Σw_j = 1`。机会价值为 `V_c = Σ(w_j × z_cj)`。分数范围自然落在 0～100，按 V 降序输出优先级。

来源数量可按本批有效来源上界归一化；记录规模可比较线性与对数变换，减轻来源样本量差异。热度先在来源内部规范化，再用于跨源汇总。权重需要说明依据，并检查合理扰动是否改变前列方向。具体权重与变换参数须由数据和研究设计确定，本报告不预设获胜主题或评分结果。

**校验：**维度和总分范围、权重和、主题对应、排序单调性、缺失热度的处理，以及相同总分时稳定且公开的排序规则。

## 8. 任务五：展示、策划案与运行条件

**输入：**任务一至四的结果及选定主题。**输出：**用户可操作的展示与 Word/Markdown 策划案。

展示至少能查看当前批次、记录来源、机会判断、主题成员、维度评分与优先级。策划案覆盖目标用户、核心痛点、核心功能、技术路线、实施周期、子任务、来源及价值评分。内容应引用真实主题证据，不从标题扩写不存在的业务事实。

角色设计需明确需求发起、数据查看、方向选择和管理操作的权限。模型 API 调用次数和费用、向量与正文存储、部署资源应有可说明的测算。配置凭据与正文分开，运行说明应能支持普通环境部署。

## 9. 实验与交付

数据获取、机会标签、主题聚类和评分分别保留可追溯版本。评估样本不能同时用于调参和最终报告；同一事件的重复内容在划分评估集时应避免泄漏。

最终提交包含：不超过 30 页正文的论文 Word/PDF、四份 CSV、源码和运行说明、全流程截图、AI 使用报告。成果中不得出现参赛身份信息。AI 工具可辅助检索、梳理、基础程序和调试，核心模型、研究判断和验证需要团队独立完成并如实记录使用情况。
